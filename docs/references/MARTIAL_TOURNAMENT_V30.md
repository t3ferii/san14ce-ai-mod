# 무술대회 v30 — 구현 참고 분석

2026-10-15, 지정 C 소스의 정적 분석. 게임에 설치하거나 원본 소스를 실행하지 않았다. 아래 줄 번호는 발췌 파일 기준이며 주석의 ‘원본 san14hook.c 줄 번호’와 다르다.

## 원본과 근거 수준

- 원본: [무술대회_코드_v30.c](../../../reference_mod/무술대회_코드_v30.c), 75,055바이트, 1,027행.
- SHA-256: `04b02e1744beaaa6aaba0fb485bff6c0574979af0662e298e268a4110944cfa3`.
- 파일 자체가 `version.dll` 프록시 SAN14Hook의 읽기용 발췌본이라고 명시한다. **완성된 빌드 소스가 아니다.** 실제로 61~63행의 enum 바깥 조각, 81행의 잘린 `pick_body`, 124행부터의 INI 읽기 조각, 공통 훅 설치/프록시 진입·해제 누락이 있다.
- [함수·호출 후보 색인](../../research/reference_deepening/tournament/source_inventory.json): lexical 후보 59개 중 본문 닫힘 확인 58개, 미완료 `pick_body` 1개. 타입·ABI를 해결한 AST나 컴파일 검증 결과가 아니다.
- ‘소스 확인’은 해당 파일이 그 동작을 작성했다는 뜻이다. ‘차용 시 확인’은 코드에서 도출한 검토 항목이며 실전에서 재현한 버그라는 뜻이 아니다.

## 먼저 확인할 호환성

소스 머리말의 대상 EXE 지문은 `07a04782…3aa40`이고 현재 디스크 EXE는 `87ed4e46590e0939c9efcaef14fa0f892917604dfda86e0a4be319fccffa2d6a`이다. 지문이 다르며 소스의 RVA를 그대로 설치할 근거가 없다.

[주소 대조 결과](../../research/reference_deepening/tournament/current_callsite_comparison.json)는 다음을 구분한다.

1. 현재 디스크 EXE의 소스 지정 CALL 9곳은 모두 예상 E8 CALL과 다르다. EXE에 `.bind`가 있으므로 **디스크 코드 불일치만으로 로드 후 코드 불일치를 확정하지 않았다.**
2. 기존 `running_code_text.bin` 평문 캡처에서도 같은 9곳이 모두 다르다. 캡처 SHA-256 `4ba3544558040f0485b0ce1a9716a6542b5eb3bbe5711ef2e88b90fecf59c179`는 `research/native_profile.json`의 평문 지문과 같고, 그 프로필의 EXE 지문은 현재 디스크와 같다.
3. 디스크의 vtable 슬롯 `0x13D6638`은 `0x14014D350`이며 소스의 `imagebase+0x44ACF0`와 다르다. 이는 디스크 자료 관찰이며 새 라이브 포인터 검증은 아니다.

따라서 **현재 프로필에 주소를 복사해 연결하면 안 된다.** 의미·호출자·원본 바이트·ABI·스레드를 재확인해야 한다. 이번 대조는 보존 캡처/디스크 기반이고 새 게임 메모리를 읽지 않았다.

## 개최·선발·대진 규칙

`TournamentTest=1`이면 첫 하루 판정에서 1회 개최를 시도한다. 정기 개최는 `TournamentMonth>0`, 같은 월, 날짜 `<=3`, 올해 미개최 조건이다(983~986). 개최 연도는 `tour_start()` 성공 전에 기록하므로 참가자가 부족해 실패한 경우도 그 세션의 해당 연도 재시도가 막힐 수 있다.

후보 선발은 무장 ID 0~6000을 돌며 신분 1~4, 유효한 비어 있지 않은 소속 세력을 수집한다. 세력별 후보는 무력 상위 3명뿐이다. 세력 병력은 도시 1~51의 `+0x3C` 합계로 **야전 부대 병력을 합산하지 않는다**. 플레이어 세력을 우선하고 다른 세력을 도시 병력 내림차순으로 뽑는다. 기본은 4세력×2명이며 부족하면 고른 세력의 남은 후보, 다음 세력으로 채운 뒤 참가 인원을 8/4/2명 중 하나로 줄인다.

이민족 제외는 ‘보유 도시가 모두 47~51’이라는 휴리스틱이다. 세력의 원작 이민족 속성을 검사한 것이 아니다. 첫 라운드는 같은 세력끼리 대결하지 않는 배치를 최대 500번 섞어 찾지만 성공을 보장하지 않고 마지막 배치를 사용한다. 4강·결승은 실제 코드 445~447행의 고정 트리를 따른다. 235행의 과거 ‘4강도 무작위’ 주석을 v30 동작으로 사용하지 않는다.

`TournamentPick` 후보 우선 처리 코드는 있지만 이 발췌본에 INI 문자열 파싱 전체가 포함됐다고 보아서는 안 된다. 이름→ID 변환과 ID 중복/동명이인 처리도 재사용 전 별도 확인한다.

## 일기토와 상태 흐름

```text
하루 판정 → 선발/대진 구성 → 개회 이벤트
                              ↓
                  (가능하면) 플레이어 두 명 선택
                              ↓
대진 안내 → 프레임 예약 → 일기토 → HP 복원/승자 수집
   ↑                                  ↓
   └──────── 다음 경기/다음 라운드 ────┘
                                      ↓
                             도시 보상 → 시상 → 폐회
```

`T`는 현재 라운드 참가자/승자/인덱스, `BR.slot[4][8]`은 표시용 대진표, `g_tour_match`는 대회 일기토 여부다. 게임 진행 상태와 표시 상태를 나누는 설계가 차용할 핵심이다.

일기토 시작 전 관리자 존재와 `+0x588` 사용 여부를 검사한다. 대회 참가자 HP `+0xF1`을 백업해 100으로 바꾸며 종료 시 복원한다. 인자에만 100을 넣는 방식이 아니라 실제 무장 필드도 바꾼다. 결과 `+0x10`이 0/1이면 해당 편을 진출시키고, 그 외는 무력이 높은 쪽, 동률이면 A를 진출시킨다. 대회 결과에서는 원래 부상·포로 결과 함수와 사기 함수를 건너뛴다.

소스에서 시작 함수의 실패 결과 처리, 게임 로드/시나리오 전환 중 정리, 재사용된 무장 ID와 원래 HP의 대응, 양쪽 모두 출전 불가인 부전승, 신분 0으로 바뀐 무장 재검증이 완결됐다고 입증되지는 않는다. HP/대사/입력 훅 같은 임시 변경은 성공 경로뿐 아니라 취소·실패·세션 교체에서도 복원하도록 설계해야 한다.

## 이벤트·선택 UI의 의존성

- `CEventPlaybackState` 생성에 `0x3905D0`을 사용하며 실제 설정은 `prm[0]=id`, `[1]=2`, `[4]=1`, `[5]=0`이다. 과거 주석에 적힌 다른 인자/함수를 복사하지 않는다. ‘결과 상태를 생략하는 종류 2’의 원작 의미는 소스 주석 설명이며 현재 게임에서 새로 확인하지 않았다.
- 글 표는 관리자 `+0x8FC48+번호*0x18`, 풀은 `+0x95A08`, 글 오프셋/길이는 엔트리 `+0xC/+0x10`이다. 길이 2~127, 풀 범위를 검사해 원문 백업→기존 자리 내 잘라 쓰기→이벤트 종료 후 복원한다. 풀을 늘리는 구현이 아니다.
- 대사 종료는 상태가 나타났다가 사라지는 것을 관찰한다. 5초 fallback은 **한 번도 나타나지 않은 경우**에만 적용된다. 나타난 상태가 계속 남는 경우의 전체 timeout은 이 코드에 없다.
- 수동 선택은 개회 종료 단계 `say_after(1)`에 연결돼 있다. `TournamentSelect=1`만으로 활성화되지 않으며 개회 이벤트, bracket, overlay 설치 성공, 플레이어 슬롯이 필요하다.
- 선택 후보는 ID순 첫 64명을 수집한 뒤 그 안에서 무력순 정렬한다. 전체 플레이어 무장의 무력 상위 64명을 보장하는 방식이 아니다. 한 페이지 24명, 3열×8행이다.
- `sel_click`의 결정 조건은 정확히 두 명이다. `TournamentPerForce=1`, 플레이어 후보 1명 또는 플레이어 슬롯 1개 등과 결합할 때 멈춤/중복 후보가 생길 수 있는지 차용 전 검사한다. 취소/키보드 대안도 발췌에서 확인되지 않는다.
- ‘한 명을 선택 가능’과 ‘우리 실제 출전자를 한 명으로 제한’은 다르다. `sel_apply`에는 1명 처리 분기가 있지만 나머지 기존 플레이어 슬롯은 남길 수 있다(569~578). `TournamentPerForce=1`도 365~366행 추가 충원 때문에 최종 한 명을 보장하지 않는다. 결정 버튼 조건만 바꾸는 것으로 출전 인원 규칙 전체를 바꿨다고 보아서는 안 된다.
- `TournamentFreeze`는 `TournamentSameDay`도 켜진 경우에만 작동한다. 날짜 정지는 원래 진행 함수 호출 중에만 관리자 `+0x10`을 임시로 켰다가 복원하며 무조건 일시정지와 다르다.

## 화면·스레드·성능

시험용 D3D11 장치/스왑체인에서 공용 vtable의 Present(8), Present1(22)를 바꾼다. 실제 렌더 상태가 아니라 공용 표를 후킹하는 방법이므로 다른 overlay·드라이버·swapchain 재생성과의 호환성이 별도 문제다. `ov_draw`는 BGRA/RGBA의 지정 형식, 비다중표본만 지원한다. 화면 높이/1080, 최소 0.5 배율로 기본 760×470 판을 만들며 WndProc 좌표는 창 크기→백버퍼→판 좌표로 변환한다.

GDI 재그리기와 texture upload는 dirty flag가 있을 때만 수행하고 표시 중 GPU 복사는 프레임마다 수행한다. 참가자 전체 탐색은 개최/선택 시작 때 수행하므로 매 프레임 6,001무장 탐색이라고 오해하지 않는다. `g_tour_cs`와 `g_ov_cs`를 나눴지만 공유 상태의 모든 읽기가 잠금으로 보호됐다고 보아서는 안 된다. 초기화·WndProc/Present 복원·리소스 해제 전체는 빠져 있으며 unload 안전성도 미확인이다.

## 우리 모드에 차용하는 방법

**대회·이벤트·선택·보상·화면 상태의 소유자는 `SAN14_Convenience.dll` 한 곳을 기본 후보로 한다.** 일기토를 사용한다는 이유로 같은 대회 훅을 전투 DLL과 편의 DLL 양쪽에서 게시하지 않는다. 기존 전투 판정과 공유하는 검증된 호출이 필요할 때만 경계 인터페이스로 분리한다. `dinput8.dll`에는 로더 기능만 두고, 원본 `version.dll` 프록시나 DINPUT8 설치본을 복사하지 않는다.

가져올 가치는 ‘2/4/8명 대진 순수 로직’, ‘상태 머신과 지연 예약’, ‘플레이어 슬롯 보존 교체’, ‘임시 HP/텍스트 복원’, ‘dirty flag 화면 갱신’이다. 현재 함수/데이터 구조를 먼저 재사용하고 새 주소를 원본 근거로 독립 검증한다. 이 문서는 무술대회 구현 요청이나 자동 설치 허가가 아니다.
