# 새 기능을 만들 때 지킬 규칙

사용자 지시 2026-11-16. 우리 모드에 기능을 새로 넣거나 기존 기능을 크게 바꿀 때 이 문서의 규칙을 모두 지킨다. 각 항목의 자세한 절차는 링크한 문서에 있다. 이 문서와 [SESSION_RULES](SESSION_RULES.md)가 다르면 SESSION_RULES가 우선이고, 이 문서를 고친다.

목표는 "기능 하나 = 모드 하나"다. 기능마다 스위치·매니페스트·검사를 갖고, 설치기는 모드 관리자처럼 켜고 끄며, 새 기능을 넣을 때는 호환 검사만 추가하면 되게 한다.

## 1. 기능의 자리를 먼저 정한다

- **소유 모듈**: `development/features.json`에 모듈 하나를 만들거나 기존 모듈에 넣는다. 파일 하나에는 소유 모듈 하나(`owns`). 검사 경로를 정할 입력 파일은 `sources`, 검사는 `routes`.
- **소유 DLL** (새 DLL·EXE는 만들지 않는다, SESSION_RULES 1절):

  | 무엇 | DLL |
  |---|---|
  | 컴퓨터 AI 판단 | `SAN14_CombatAI.dll` |
  | 조조전 탭 기능 | `SAN14_CCZ.dll` |
  | 다른 모더 패치 이식 | `SAN14_ModPack.dll` |
  | 화면 훅 기반(레이아웃 체인) | `SAN14_Layout.dll` |
  | 그 밖의 모든 기능 | `SAN14_Convenience.dll` |

- **진입점**: 지도·도시 메뉴·군사보고·설치기·자동 AI 중 어디서 여는지 적는다. 다른 기능의 UI로만 열리면 그 기능의 자식이다([기능 추가·수정 체크리스트](FEATURE_CHANGE_CHECKLIST.md) 1절).
- **적용 대상**: 컴퓨터 규칙은 플레이어가 직접 지휘하는 군단과 위임 군단에 적용하지 않는다. 플레이어용 기능이거나 날씨처럼 모두에게 같은 규칙이면 문서에 그 이유를 적는다.

## 2. 스위치: 끄면 원작

- 설정은 `기능설정.ini` 한 곳, 키 하나. 같은 변경 안에서 `development/installer_map.json`에 행을 넣고 `tools/gen_installer_catalog.py --apply`로 설치기 카탈로그를 다시 만든다(SESSION_RULES 2절).
- DLL에서는 `load_mod_features()`에서 `f.키 = f.부모 && feature_key(config, L"섹션", L"키", 기본값)`. 코드 기본값은 안전한 쪽(대개 0), 사용자가 원하는 기본값은 설치기에 둔다.
- **스위치가 꺼졌거나 DLL이 없으면 원작 동작, 또는 그 전에 깔린 다른 모드의 동작**이어야 한다. 기능이 만든 UI(버튼·레이아웃 행·글자)도 함께 원래대로 돌아가야 한다([UI 리소스 기준](UI_RESOURCE_LIFECYCLE.md) 8절).
- 여러 기능이 쓰는 엔진 서비스(예: 지형 엔진 `terrain_core_on()`)는 쓰는 기능 스위치들의 OR로 켠다. 서비스 자체 스위치를 만들지 않는다([내부 호환 규칙](MOD_INTEROP_SPEC.md) 2절).

## 3. 훅과 패치

- 원작 주소는 주소표 id(`GA(GA_...)`, `src/game_addresses.h`)로만 쓴다. 기능 코드에 RVA 숫자를 쓰지 않는다(`tools/check_addresses.py`). Steam 패치로 주소가 바뀌어도 주소표만 고치면 되게 한다([패치 대응](PATCH_RESILIENCE.md)).
- 새 훅·바이트 패치·vtable 교체마다 **원래 바이트 가드**(`<기능>_guards_match()`)를 두고, `src/native_split_install.inl`에 `if(f.<기능> && !<기능>_guards_match())split_disable(f.<기능>,<코드>);`를 넣는다. 다른 모드가 그 자리를 이미 고쳤으면 그 기능만 꺼지고 나머지는 동작한다. 전체 `.text` CRC를 동작 조건으로 쓰지 않는다.
- 훅 하나에는 소유자 하나. 훅 정책(chain·yield·refuse·refuse_if_changed·exclusive)을 정하고, vtable 슬롯은 `layout_registry.h` 행 + `ROUTE_VT(slot, original, repl, &next)`로 건다. 대체 함수는 원작 주소가 아니라 `next`를 부른다. 자리는 `development/hook_sites.json`에 적는다([내부 호환 규칙](MOD_INTEROP_SPEC.md) 1절).
- 패치 기본 함수(`prepare_bytes`·`patch_pointer`·`replace_code16`·`modpack_write` 등)는 core 서비스로 부른다. 서비스 밖 직접 호출(feature_deps D6)은 늘리지 않는다.
- 같은 자리를 두 모듈이 번갈아 쓰면 HOOK 기준선(`development/feature_deps_policy.json`)에 사유와 함께 적는다. 사유 없는 공유는 실패다.

## 4. 게임과 상호작용하는 방법

- 원작 함수는 게임의 UI·AI 스레드에서만 부른다. 외부 프로세스의 메모리 쓰기·원격 호출은 하지 않는다.
- 게임 효과(병력·사기·식량·지형·소식 등)는 **원작 함수에 훅을 걸어 결과를 바꾸거나, 게임 스레드에서 원작 함수를 불러서** 만든다. 게임 메모리를 직접 고쳐 효과를 내지 않는다(사용자 2026-11-13).
- 저장: 원작 세이브 형식은 바꾸지 않는다. 기능 자료는 `src/save_host.h`의 사이드카(`SidecarPlugin`)로 따로 저장하고, 모드 없이 세이브를 불러도 안전해야 한다.
- 구조체 오프셋·함수 의미는 `San14Sim/docs/orig` → `tools/decomp_cache.py` → `tools/ghidra_full.py` 순으로 근거를 찾는다. 의사코드는 가설이며 바이트·호출자로 확인한다. 게임 EXE에 REA는 쓰지 않는다.

## 5. 모듈 경계 (feature_deps)

`tools/feature_deps.py --check`가 막는 규칙이다. 새 기능은 기준선(ratchet) 숫자를 늘리지 않는다.

| 규칙 | 지킬 것 |
|---|---|
| D1 | 모듈 사이 코드 의존은 `depends`에 선언된 방향으로만 |
| D10 | 선언되지 않은 순환 금지 |
| D2 | 다른 DLL의 심볼을 쓰지 않는다 |
| D3 | 파일은 소유 모듈의 DLL에만 컴파일된다 |
| D4 | 다른 모듈 함수를 앞 선언해서 부르지 않는다. 그 모듈이 소유한 헤더를 포함한다 |
| D5 | 다른 모듈의 스위치(`mod_features.x`)를 직접 읽지 않는다 |
| D6 | 패치 기본 함수는 서비스로 |
| HOOK | 공유 훅 자리는 기준선에 사유와 함께 |

- "X가 켜져 있으면 함께 동작" 같은 느슨한 연결은 `depends`에 넣지 않는다(`depends`는 설치기에서 필수 의존으로 보인다). 허브 `split_bind_links()`에서 함수 포인터와 스위치 주소로 연결한다([내부 호환 규칙](MOD_INTEROP_SPEC.md)의 「모듈 사이 연결」).
- 두 DLL이 함께 보는 계약 헤더는 core 소유 서비스 파일로 둔다.

## 6. 자산과 생성물

- 소스로 만들 수 있는 것은 모두 git의 소스와 스크립트로 만든다: DLL은 `tools/build_split.ps1`, 설치기는 `tools/build_installer.ps1`, 셰이더는 `.hlsl` + 빌드 스크립트, 모듈 표는 `tools/gen_module_table.py`.
- 생성한 헤더·표(`Generated by ...` 머리말)는 만든 스크립트를 git에 두고, 그 스크립트의 입력이 git 밖(research·data·build)에만 있으면 안 된다.
- 다른 모더의 자산·코드를 가져오면 출처·버전·해시를 기록하고(예: `src/season/season_engine.c` 머리말), 배포물의 README·읽어주세요·설치기 설명에 크레딧을 적는다([크레딧](CREDITS.md)).
- 큰 바이너리 자산(텍스처·스프라이트)은 git에 넣지 않되, 생성기 또는 출처 기록과 SHA-256을 manifest에 남긴다.

## 7. 진단

- 로그는 공용 `log_event`만 쓰고, 진단 코드는 `#ifndef NO_RUNTIME_LOG` 안에 둔다(배포판에서 빠진다). 진단 스위치는 `[diagnostics]` 묶음(`groups.diagnostics`) 아래.
- 새 기능은 설치 결과를 한 줄 남긴다: `<기능>_installed`(켜짐 여부·실패 코드). 이 줄이 [실게임 최소 확인](RUNTIME_SMOKE.md)의 기준이 된다.
- 원인을 모르는 문제는 추측으로 고치지 말고, 다음 빌드에 진단 지점을 넣어 한 번에 확인한다.

## 8. UI

- 원작 UI를 흉내 내지 말고 원작 버튼·창을 복제해서 쓴다. 먼저 [UI 추가 안내](UI_ADD_GUIDE.md)의 정답 요약을 읽는다.
- 레이아웃 뱅크 24~31은 모드용이다. 화면 자료를 바꾸면 `install_local.py --layout`으로 설치한다.
- 이미 실패한 방식(버튼 생성 시점·선택 모드·전체 저장·내부 클리핑·외교 퇴장)을 다시 쓰지 않는다([UI 실패 기록](UI_FAILURES_AND_RECIPES.md)).

## 9. 검사

- 새 동작에는 모의 검사(fixture)를 추가하고, `development/features.json` `routes`에 경로를 둔다. 설치기 문구·패치 수 같은 값은 검사에 박지 말고 카탈로그(`installer_map.json` 등)에서 읽는다.
- 개발 중: `tools/check_feature.ps1 -Feature <기능> -List` → 그 경로. 공용 파일을 건드렸으면 그 파일을 쓰는 경로도.
- 설치 직전: `tools/build_split.ps1 -RuntimeDiagnostics`, `check_feature.ps1 -Feature dll-split -Build`.
- **검사가 실패하면 검사를 고치거나 모드를 고친다.** "원래 실패하던 것"으로 넘기지 않는다.
- 모의 검사 통과는 실게임 확인이 아니다. 보고에서 둘을 구분한다.

## 10. 문서

같은 변경에 포함한다.

- 기능 문서(진입점·화면 흐름·꺼졌을 때 동작), [FEATURE_SWITCHES](FEATURE_SWITCHES.md) 행, [MODULES](MODULES.md)(생성).
- 원작과 달라진 규칙·훅 지점: [MOD_CHANGES_VS_ORIGINAL](MOD_CHANGES_VS_ORIGINAL.md). 원작 사실은 `San14Sim/docs/orig`에만.
- 시행착오: [MOD_DEV_LESSONS](MOD_DEV_LESSONS.md). 설치·배포 기록: [CHANGES_ALL](CHANGES_ALL.md), `development/CURRENT.md`(생성기).

## 11. 설치와 배포

- 설치는 게임을 끈 상태에서 `tools/install_local.py prepare/install`로만(SESSION_RULES 5절). 배포는 [PUBLISH](PUBLISH.md) 순서만 따른다. 배포물은 미서명이라고 적는다.
