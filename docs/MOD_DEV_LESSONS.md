# 모드 개발 시행착오와 재발 방지 규칙

새 기능(모드)을 만들 때 **설계 전에 한 번** 읽는다. 각 항목은 실제로 시간을 잃은 사례이고, 마지막 줄이 지킬 규칙이다. UI 증상별 상세는 [UI 실패 기록](UI_FAILURES_AND_RECIPES.md) §9, UI 소유 구조는 [UI 리소스 기준](UI_RESOURCE_LIFECYCLE.md) §10.

주소는 현재 Steam 빌드(1a4a447d) 기준이다. 정적 근거: `research/ghidra_full/1a4a447d14e68c40/c/`.

## A. 원작 구조를 잘못 짚은 경우

### A1. 비슷한 구조체를 같은 것으로 봄 (전법 우선순위 local15)
- 출진 화면의 편성 기록 목록(`state+0x4C0`)과 출발 목록(`+0x540`)을 같은 구조로 보고, 출발 목록의 `item+4` 오프셋을 편성 기록에도 적용했다. 편성 기록은 0x94바이트 구조체 자체여서 인물 +0, 병력 +8, 진형 +0xC, 전법 +0x14/+0x18/+0x1C다. 그 결과 모든 행이 필터에서 탈락하고 로그에 "부대 2개"만 남았다.
- **규칙:** 필드 오프셋은 그 목록을 **직접 읽는 원작 코드**(삭제·생성·후처리 함수)에서 확인한다. 이름이나 모양이 비슷한 다른 목록의 오프셋을 옮겨 쓰지 않는다. 계획서의 오프셋에는 근거 함수와 줄을 같이 적는다.

### A2. 화면의 살아 있는 원본은 편집 버퍼였음
- 원작은 오른쪽 창의 편집 버퍼(`page(+0x490)+0x178`, 0x94바이트)를 선택 기록(`list[+0x4E4]`)에 통째로 복사한다(`FUN_1407ea2d0`). 그래서 기록에만 쓰면 다음 편집 때 덮어쓰인다.
- **규칙:** 원작 화면에 값을 써야 할 때는 먼저 "화면이 어디서 값을 읽고, 어디로 복사하는가"를 찾는다. 원본(버퍼)과 사본(기록)을 같이 쓰고, 원작의 갱신 호출로 다시 읽힌다.

### A3. 포인터가 0이 아니다 ≠ 모달이 열렸다
- `state+0x4B0`는 화면이 항상 들고 있는 출발 확인 대화 객체였다. 이를 "모달 열림"으로 보고 팝업 열기를 매번 거절했다. 원작은 `+0x4B0 != 0 && FUN_140870ed0()`(층 목록에 활성으로 있음)일 때만 입력을 막는다.
- **규칙:** 상태 판정은 원작이 쓰는 조건식을 그대로 옮긴다. 포인터 존재만으로 상태를 추정하지 않는다.

### A4. 현재 선택 = 목록[선택 번호]
- 현재 부대는 `list[state+0x4E4]`(부대 목록 컨트롤의 선택 번호)다. 탭 그룹 `+0x148`도 같은 포인터이지만, 전역 핸들 표를 거쳐 들어오므로 해석을 헷갈렸다.
- **규칙:** "현재 선택"은 원작의 선택 이벤트 함수가 쓰는 값에서 가져온다.

### A5. 옆 코드의 주석을 원작 사실로 옮겨 씀 (세력 +0x52 = 군사를 군주로, local18→local248, 2026-11-19 정정)
- 자동 포상(local18)이 원작 717130이 세력 +0x52를 읽는 것을 보고 그 칸을 "군주"라고 적었다. 717130이 그 칸을 읽는다는 것은 위치만 알려 줄 뿐이고, 뜻은 structs.md가 말하듯 **군사**다. 그 뒤 장수 순환·매복·컴퓨터 교역·의용병이 "auto_commands처럼" 그 줄을 옮겨 써서 다섯 기능이 군사를 군주로 썼다. structs.md(2026-11-07)에는 처음부터 +0x10 군주, +0x52 군사였고, 조조전 그림은 처음부터 맞게 읽었다.
- 규칙이 없어서가 아니다: A1이 이미 "다른 곳의 오프셋을 옮겨 쓰지 않는다"고 적고 있었다. local248(의용병)은 원작 지식 문서를 열지 않고 장수 순환의 주석 "force +0x52, as auto_commands reads it"를 그대로 옮겼다.
- 오래 안 드러난 이유: 군주와 군사가 같은 성에 있으면 결과가 같다. 군사가 다른 성에 있거나 탐색을 나갈 때만 틀린다(의용병이 오에서 생기고, 10일마다 위치가 바뀜).
- **규칙:** 구조체 칸의 뜻은 `San14Sim/docs/orig/structs.md`(없으면 그 칸을 쓰는 원작 함수의 쓰임새)에서 확인하고, 소스 주석에 그 근거를 적는다. "원작 함수 X도 이 칸을 읽는다"는 칸의 위치만 알려 주고 뜻은 알려 주지 않는다. 우리 코드의 다른 기능 주석은 근거가 아니다. 결과가 맞아 보여도 두 값이 같아지는 흔한 상황(같은 성)이 아닌 경우로 확인한다.

### A6. 튕김 수정 요청에 원인 밖 경로를 조사함 (의용병 지휘관 주의, local260, 2026-11-19)
- 진단이 "지휘관 주의 0이 플레이어 세력 무장으로 세어져 22B360 배열 밖을 쓴다"까지 확정했는데, "왜 세력 2로 읽히나"를 원작 제거 함수 `25A880`에서 찾다가 우리 훅 범위를 확인하지 않고 원작 분기 탓으로 결론 냈다(`hook_remove`가 local217부터 제거 중에는 원래 세력 51로 답하고 있었다). 무리가 플레이어를 따르는 것은 설계 그대로였다. 사용자: "그걸 왜조사하는거야 대체? 튕긴 원인만 고쳐".
- **규칙:** 튕김은 쓰기 지점(여기선 주의 값)을 바로 막는다. 의도된 설계(종군 = 주인 세력)를 원인으로 의심하기 전에 설계 문서와 사용자 시나리오를 먼저 대조한다. 디컴파일 분기를 원인으로 쓰기 전에 그 함수에 걸린 우리 훅과 범위(`FaceScope` 등)를 먼저 본다.

### A7. 범위 검사만 하고 필드 뜻은 안 읽음 (다중 일기토 슬롯 +0xD0, local274→local275, 2026-11-20)
- 원작 슬롯 함수가 "슬롯 밖을 건드리지 않는다"는 것만 훑고, 슬롯의 `+0xD0`을 사양서대로 "이동 목표 x"로 보고 옆 간격을 더했다. 설치 후 `376450` 본문을 읽어 보니 `+0xD0`은 `14BDA30`(0,0,0,1)을 넣는 회전 쿼터니언이었고 이동 목표는 `+0xE0`(`37D930`)이었다.
- **규칙:** 원작 구조체 칸에 값을 쓰기 전에, 그 칸을 채우는 함수 본문과 넣는 상수값, 그 칸을 읽는 함수를 직접 읽는다. 범위 스캔은 안전성만 알려 주고 뜻은 알려 주지 않는다(A5와 같은 뿌리).

### A8. 장면 경계를 상태 값의 0 순간으로만 잡음 (다중 일기토 연속 장면, local275→local276, 2026-11-20)
- 일기토 장면의 시작을 "장면 진행 `+0x588`이 0으로 읽힌 뒤 다시 1"로만 알아서, 같은 날 건너뛴 장면 바로 뒤의 일기토(조운–후음)를 보지 못했고 로그도 남지 않았다. 사용자가 원작 기록으로 알려 줌.
- **규칙:** 원작 장면·창을 따라갈 때는 진입 함수(여기서는 호출자 하나인 `376020`)를 잡아 장면마다 번호를 센다. 상태 값의 경계는 한 프레임 안에 끝나고 다시 시작하면 보이지 않는다. 조용히 끝나는 분기마다 장면당 한 번 로그를 남긴다(D1).

### A9. 원작이 지우지 않는 칸을 "새로 채워졌다"로 읽음 (다중 일기토 슬롯, local276→local277, 2026-11-20)
- 장면 진입 직후 슬롯의 모델 `+0x1B0`이 있으면 원작이 슬롯을 다시 만든 것으로 봤는데, 원작 정리 `37D040`은 무장 `+0xB0`·모델 `+0x1B0`을 지우지 않아 두 번째 장면부터 지난 장면 무장을 읽었다.
- **규칙:** 원작 객체 칸이 "이번 것"인지는 채우는 단계(여기선 상태 1 `37A170`)가 끝났다는 신호와 진입 값 대조로 정한다. 정리 함수가 무엇을 지우는지 먼저 읽는다.

### A10. 카메라 방향을 추측해 자리를 두 번 옮김 (다중 일기토 추가 무장, local276→local278, 2026-11-20)
- 추가 무장이 안 보이자 "옆에서 찍는 카메라" 추측으로 x 옆(local276) → z 뒤(local277)로 옮겼고, 카메라 후보로 일기토 전역을 훑었지만 단서가 없었다. 카메라 사슬과 행렬 배치는 이미 `docs/NATIVE_FUNCTIONS.md` ccz_sprites 줄에 있었다.
- **규칙:** 화면에 보이는지 문제는 먼저 NATIVE_FUNCTIONS에서 카메라를 찾고, 원작 대상(여기선 원작 무장 둘)을 그 ViewProj로 투영해 "이 카메라가 맞다"를 확인한 뒤 같은 투영으로 자리를 정하고 화면 좌표를 남긴다.

## B. 원작 UI 생성·소멸

### B1. 만든 창이 안 보임: UI 관리자 등록 누락
- `870410`+컨트롤만 만들고 `vt+0x38`(`FUN_140869210`, 표 초기화와 UI 관리자 층 목록 등록)을 부르지 않아, 창은 생겼지만 그려지지 않았다. 로그에는 "생성 성공"이 남는다.
- **규칙:** 원작이 새 레이아웃을 만든 뒤 부르는 순서(생성 → `vt+0x38`)를 그대로 따른다. 생성 성공 로그와 화면 표시는 별개로 확인한다.

### B2. 숨김은 해결이 아님: 원작 소멸 순서
- 처음에는 "부모가 자식을 해제하지 않는다"는 이유로 팝업을 숨긴 채 남겼다(화면 진입마다 누수). 사용자 지적으로 원작 순서를 찾았다.
- 원작 소멸 순서: `vt+0x40(obj)`(층 목록 제거) → `vt+0x28(obj,next)`(컨트롤 소멸, 부모 풀에서 제거) → `vt[0](obj,1)`. 자식은 부모보다 먼저 없앤다.
- **규칙:** 만든 UI 객체는 반드시 원작 소멸 순서로 지운다. 숨김·누수·"튕길까 봐 안 지움"은 해결책으로 쓰지 않는다.

### B3. UI 진입점은 Layout DLL, 동작은 모드
- 처음에는 기능 모듈이 창을 직접 만들었다. 사용자 규칙: UI(진입점)는 SAN14_Layout.dll이 만들고·배치하고·지우고·클릭을 전달한다. 모드는 콜백 뒤의 동작만 가진다. 설치기 기능 스위치 하나가 둘을 같이 켜고 끈다(`ui_begin(owner)`가 게시 상태일 때만 성공).
- **규칙:** 새 버튼·팝업·토글은 처음부터 `layout_api.h`의 `ui_*`로 만든다.

### B4. 원작 설명자 창은 표를 못 그리고 틀 그림이 안 붙을 수 있다
- 군사보고 본문 창(2026-11-07)을 원작 설명자 창(type 8 프레임 + type 1 글자 줄)으로 옮겼더니 프레임 배경 텍스처가 붙지 않아(요소 `+0x112 = 0`) 글자가 맨 화면 위에 떴고, 글자 줄만 있어 군단별 수입 표가 한 줄 문장으로 납작해졌다. 사용자가 실게임에서 보고서야 알았다. 모양보다 먼저 기능 전체를 얹어 둔 탓에 폐기와 되돌리기에 한 라운드가 더 들었다.
- **규칙:** 원작 UI 요소로 창을 옮기기 전에 그 요소가 (1) 배경·틀을 실제로 그리는지, (2) 필요한 레이아웃(표·정렬)을 표현할 수 있는지를 프로브·스크린샷 빌드 하나로 먼저 확인한다. 확인 전에는 그 위에 기능 전체를 만들지 않는다. 표가 필요한 화면은 모드 자체 렌더러(오버레이)가 기본이다.

- (local299) 카메라 회전 "규약" 맞추기를 원작 회전의 절대값 비교로 했더니 네 후보가 모두 30° 숙임 차이로 탈락했다(`duel_manual_qcheck` 2). 쓸 회전을 원작 회전 위의 차이로 만들고(네 곱 조합), 쓴 같은 틱에 카메라 블록을 되읽어 앞·위가 맞는 조합만 잡는다 — 다른 조합과 거의 같으면(6° 안) 고정하지 않는다. 판정이 안 되는 경우를 위해 회전 없이 원작 시선만 물리는 대체 길을 같은 빌드에 넣었다.
- (local299) G7 세 번째: 색 상수 `0x2b1913` 같은 #rrggbb 리터럴 27개가 `check_addresses` (b)에서 주소 모양으로 걸렸다. 색은 처음부터 바이트 세 개(`Rgb{43,25,19}`)나 실수로 쓴다.
- (local300) local299의 "원작 회전 위 차이"도 실패: 원작 카메라의 저장 회전(getter)은 그 화면이 아니었다(항등인데 블록은 30° 숙임). 그 회전을 기준으로 쓴 것은 전부 기준만큼 어긋난다. 반대로 우리가 쓴 회전은 모두 블록에 그대로(R(q)·z = 앞, R(q)·y = 위) 나왔다 — **규칙:** 원작 객체의 저장값이 화면을 설명한다고 가정하지 말고, 우리가 쓴 값이 어떻게 되읽히는지를 기준으로 삼는다. 판정 로그에는 처음부터 원시값(q와 되읽은 앞·위)을 남겨 다음 판에 오프라인으로 모형을 맞출 수 있게 한다(local299 `duel_manual_qraw`가 이번 결론의 근거).
- (local300) 연출 하나(원 돌기)를 실패할 수 있는 다른 장치(옆 카메라)에 묶어 두면, 그 장치가 안 켜질 때 사용자가 원한 연출까지 통째로 사라진다(local298·299 두 판 연속 제자리 질주). 독립적으로 보여야 할 연출은 따로 켜고, 실패 대체 길도 같은 연출을 유지하게 짠다.

### B5. 그림 이름과 노드 사각형만 보고 쓸 곳을 정함 (릴레이 일기토 local298, 2026-11-22)
- `07_base_buryoku`를 "붓 판", `07_base_draw_01`을 "먹 판"으로 믿고 명령 창을 짰는데, 실게임에서는 「무력」 글자 그림과 큰 흰 붓글씨(무승부)였다. 메달 숫자도 120 × 120 사각형이 같은 자리라 0x1B~0x1F를 숫자로 보고 숨겼지만, 실제 숫자는 0x36·0x37이었다(`827D70`이 `07_num` 그림을 붙임). 둘 다 그 판을 실게임에서 처음 봤다.
- **규칙:** 원작 그림을 새 용도로 쓰기 전에 그 그림을 실제로 본다(프로브 빌드의 화면 한 장, 또는 그 그림이 원작에서 쓰이는 화면). 원작 노드를 숨기거나 바꾸기 전에는 그 노드에 그림을 붙이는 원작 함수를 찾는다(그림 id 상수를 `ghidra_full.py grep`). 사각형 위치만으로 정하지 않는다.
- (local301) 원작 화면 조각을 일부만 다시 채우면(일기토 게이지의 얼굴·이름·무력만) 나머지(개성 칸)가 옛 무장 것으로 남아 "효과도 옮겨 갔나"라는 오해를 만든다. 원작 생성 함수(`809110`)가 그 화면에 채우는 칸 목록을 먼저 다 적고 갱신 때 같은 목록을 다룬다. 다른 DLL(ModPack traits9 9칸)이 같은 칸을 덮는 화면은 그 DLL의 상태를 편의 DLL이 못 보므로(`services` 인스턴스가 DLL마다 따로) 그 DLL의 판정식(traits9 화면 규칙 26B0)으로 겹칠 편을 미리 가려 건드리지 않는다. 그 모듈의 헤더를 include하면 `feature-deps` D1(모듈 간 새 의존, 엄격)에 걸린다 — 한 줄짜리 규칙은 출처를 주석에 적고 옮겨 쓴다.
- (local301) 실행 중에만 정해지는 글자(무장 이름)는 미리 구운 마스크로 못 그린다 — Present 스레드에서 GDI(회색조 안티에일리어싱, `ANTIALIASED_QUALITY`)로 그려 같은 테두리 처리를 씌우고, 값이 바뀔 때만 다시 만든다(UI 스레드 → seqlock). 오버레이 고정 검사(`shared-overlay`)에 그림 파일 출력 환경 변수를 두면 실게임 전에 모양을 눈으로 확인할 수 있다(`SAN14_DUEL_PREVIEW_PICK`).
- (local303) Present에서 CPU로 굽는 텍스처는 실게임 로그의 만들기 시간(`duel_manual_sticker_build` hex ms)을 먼저 본다 — 스티커 한 장 49 ms라 아홉 장을 한 프레임에 구우면 0.4초 멈춘다. 종류별로 한 프레임에 하나씩 굽고 종류마다 준비 비트를 UI 스레드에 알려(`sticker_ready(kind)`), 아직 없는 종류만 예전 표시(자막)로 둔다. 무작위 모양(폭발 가시)을 씨앗만 바꿔 재사용하면 캔버스 크기 공식이 가장 긴 가시를 덮는지 다시 확인한다(미리보기 그림에서 가시가 잘려 보였음).

## C. 주소표·빌드

### C1. `static const` 주소는 빌드 선택 전에 굳는다
- `static const unsigned k=GA(...)`는 정적 초기화 때 계산되어, 빌드 표를 고르기 전 값(0)으로 굳었다.
- **규칙:** `GA(GA_x)`는 쓰는 자리마다 바로 적는다. 접근 함수로 감싸면 hook_map이 못 읽는다.

### C2. 새 GA id는 스캐너가 모른다
- 새 파일에서 쓰는 id는 `tools/gen_signatures.py`의 기능별 EXTRA 목록에 넣어야 한다. 호출 위치(mid) id는 remap 상태가 비면 새 빌드에서 0이 되므로 `b_verdicts.json` 판정이 필요하다.
- `gen_signatures.py all`은 작업 폴더에서 돌려도 `research/` 정션을 거쳐 본체의 `addr_table.json`을 덮어쓴다. `build/rebase_logs`가 없으면 불완전본을 쓴다.
- **규칙:** 새 id는 EXTRA 목록과 판정까지 같이 넣는다. 재생성 전에 `build/rebase_logs`를 확인하고, 재생성 후 `data.inl` 개수와 `addr_table.json` 개수가 같은지 본다.

### C3. 공용 목록에 행을 더하면 그 목록을 박아 둔 검사가 따로 있다 (local298, 2026-11-22)
- 오버레이 구독 행 duel_digits를 레지스트리에 넣고 생성기·기능 검사는 통과했는데, `check_feature -Changed`에서 `tests/core_services_fixture.cpp`가 실패했다(그리기 순서·게이트 순서·svc_install 해시 세 곳에 주인 이름 목록이 박혀 있음). 같은 날 다른 세션의 사이드카 플러그인 크기 변경(8 → 12)은 `tests/verify_traits9_save.py`의 저장 소스 해시 고정을 깼다.
- **규칙:** 공용 목록(`services::*` 구독, 사이드카 플러그인, 저장 소스)에 행을 더하거나 크기를 바꾸면 그 이름·해시를 tests/에서 먼저 Grep해 기대값을 같은 커밋에서 고친다. 저장 소스 해시는 형식이 그대로인지 검토하고 메모를 남긴 뒤에만 바꾼다.

## D. 진단

### D1. 조용한 조기 반환
- `open_popup`이 아무 로그 없이 빠져나가서, 클릭 로그만 있고 원인을 알 수 없었다.
- **규칙:** 새 기능의 모든 조기 반환은 이유 번호를 로그로 남긴다(`*_skipped reason`).

### D2. 새 화면 훅의 첫 빌드에는 진단 장치를 넣는다
- 실행 중인 게임 메모리를 vtable로 찾으려 했지만 화면 객체를 찾지 못했다. 시간만 잃었다.
- **규칙:** 원작 화면에 처음 붙는 기능은 첫 빌드부터 진단판 전용 덤프를 넣는다. 덤프는 화면 진입·선택 변경 때 상태 필드, 선택 행, 편집 버퍼의 원시 값이다. 다음 테스트 한 번으로 구조가 확정된다.

### D3. 스레드
- 같은 갱신 슬롯이 처음엔 입력 스레드, 이후엔 다른 스레드에서 불렸다. 클릭 콜백은 큐에만 넣고, 원작 함수 호출은 갱신 훅 안에서 한다.

### D4. 로그 시각과 CSV 틱을 시스템 시계로 맞춤 (순 끊김, 2026-11-16)

- 무슨 일: 화면 멈춤(`perf_spike`, 로그 초 단위)과 `function_stall_*.csv`(GetTickCount64 ms)를 지금 시각과 TickCount의 차로 맞췄다. 15분 사이 약 1초가 어긋났는데, 모든 순에서 순 처리가 멈춤보다 0.5~1초 앞이라 "순 처리가 원인"으로 잘못 보고했다. 사용자가 "전략 차례에서 끊긴다"고 짚은 뒤 다시 맞추니 멈춤은 컴퓨터 세력 전략 차례와 겹쳤다.
- 규칙: 로그와 CSV는 같은 프로세스가 남긴 기준점으로 맞춘다. `day_stage` 줄의 hex가 GetTickCount64이므로, 줄마다 (로그 초 − hex)를 구해 겹치는 구간으로 오프셋을 정한다(대개 폭 0~200ms). 결과가 "늘 1초 앞선 사건"을 가리키면 오프셋부터 의심한다. 넓은 창(±1초)으로 겹침을 세면 앞선 사건이 거의 다 맞은 것처럼 나온다.

### D5. 표본기와 비용 CSV가 보는 범위 (전략 차례 끊김, 2026-11-16)

- 무슨 일: local203 표본기 결과로 "명품 대조와 계측이 전략 AI 시간의 절반"이라고 결론 낼 뻔했다. 확인하니 네 가지가 틀려 있었다. (1) 초당 `function_cost_*.csv`는 깊이 0 범위가 창을 연 지 1초 지나서 끝날 때만 쓰므로, 제출마다 새 스레드에서 도는 세력 AI(`native_ai_root`)를 거의 담지 못했다(진행 로그 합 약 75초, CSV 2.1초). (2) 표본기 스택은 "CALL 바로 다음 주소처럼 보이는 스택 값"이라 오래된 값이 섞인다(렌더 사슬에 `_register_onexit_function`, 길찾기 아래 `award_filter_iterator`). (3) 첫 표본이 80ms가 아니라 160~240ms에 찍혀 긴 멈춤의 끝부분만 봤다. (4) 50ms 넘는 `native_ai_root` 307개를 멈춤 구간과 맞추니 하나도 겹치지 않았다. 멈춤은 세력 AI 시작 약 70ms 전에 끝난다.
- 규칙: 짧게 사는 스레드의 비용은 즉시 기록(`function_stall`)으로 본다. 원인 후보는 시작·끝 틱이 멈춤과 겹치는지부터 확인한다. 표본기는 RIP와 첫 후보만 믿고, RIP가 Wait/Delay인 대기 표본을 먼저 뺀 뒤 비율을 낸다. 한 판 안의 추세는 "같은 일 한 번의 비용"(호출당 시간)과 "일의 양"(호출 수·부대 수)을 나눠 본다.

## E. 사양을 미리 확정하지 않음

### E1. "우선순위"의 뜻
- 우선순위를 "순서만"으로 설계해서 지정하지 않은 칸을 기본 순서로 채웠다. 사용자가 원한 것은 "지정한 것만"이었다. 출진 기억도 "기억한 것 먼저, 나머지 채움"으로 설계해서 1개만 기억해도 3개가 나갔다.
- **규칙:** 계획 단계에서 동작이 갈리는 질문을 사용자에게 먼저 확인한다. 이번 사례에서는 빈칸을 채울지, 실시간 적용인지, 개인 규칙과 공통 규칙 중 무엇이 우선인지였다. 계획서에 "결정된 사양" 절을 두고, 사용자 답이 없는 항목은 구현 전에 묻는다.

### E2. 이미 있는 우리 기능을 먼저 본다
- 전법 설명 마우스오버를 원작 코드에서 새로 찾으려 했다. 우리 `trait_hover` 모드가 이미 게임 데이터로 전법 설명을 만든다.
- **규칙:** 새 기능에 필요한 부품은 `development/features.json`과 `docs/FEATURE_SWITCHES.md`에서 기존 모드부터 찾는다. 재사용할 때는 `depends`로 의존을 선언한다.

## F. 작업 방식(에이전트)

### F1. 검사 대기 작업 폭증
- 작업서의 "긴 검사는 백그라운드로 돌리고 기다려라"를 Sonnet이 검사마다 대기 작업을 띄우는 식으로 해석해서, 대기 작업이 30개 넘게 쌓였다.
- **규칙:** 작업서에 "검사는 하나씩 순서대로 화면 앞에서(timeout ≤600000ms), 백그라운드·감시·대기 작업 금지, 10분 넘는 검사는 나눠서"를 적는다. 보고가 끝난 에이전트가 계속 실행 중으로 보이면 멈춘다.

### F2. 계획이 틀리면 코딩 에이전트가 조사까지 떠안는다
- v2 계획의 오프셋·조건 오류 때문에 구현 에이전트가 원작 조사부터 다시 했다. 그래서 느려졌다.
- **규칙:** 계획서의 원작 사실(오프셋·조건·호출 순서)에는 근거 함수와 줄이 있어야 한다. 근거가 없는 항목은 "미확정"으로 표시하고, 첫 빌드의 진단 장치(D2)로 확인한다.

### F3. 작업 폴더 찌꺼기
- `git worktree remove` 뒤에도 build 폴더와 그 안의 정션이 남았다.
- **규칙:** 작업 폴더를 지울 때는 정션을 먼저 `rmdir`로 끊는다(대상은 지우지 않음). 정션이 하나도 없는지 확인한 뒤 폴더를 지운다. 정션을 둔 채 재귀 삭제하지 않는다(본체 research·backup이 지워질 수 있음).

### F4. 중간 결정이 바뀌면 바로 전달
- 사용자 결정(적용 버튼 취소, 지정한 것만, 마우스오버 재사용)은 실행 중인 에이전트에 즉시 보냈다. 커밋 없이 멈춘 에이전트의 수정분은 WIP 커밋으로 살려 새 에이전트가 이어 받았다.
- **규칙:** 에이전트는 작업 단위마다 커밋하게 한다. 중간 상태도 복구할 수 있어야 한다.

## 거점 수복 부대에서 배운 것 (2026-11-12, local75~local94)

스무 번 가까이 고쳐서야 맞았다. 원작 동작을 모르고 짐작으로 시작한 탓이다. 원작 쪽 사실은 `San14Sim/docs/orig/ai/roles.md` 6-4절에 모았다.

- **원작 조건을 풀어서 원하는 출진을 얻으려 하지 말 것.** 지역 점령 출진의 "적이 가까우면 안 나감" 관문을 네 곳 풀었지만 한 번도 나오지 않았다(local80~83). 관문이 몇 겹인지 모를 때는 모드가 직접 출진시키는 쪽이 빠르다.
- **모드가 만든 군세는 원작 군세 판단표가 매 턴 고쳐 쓴다.** 종류 10·목표 = 자기 성으로 내보낸 부대를 원작이 요격 군세로 바꿨고, 그것이 "적에게 빨려 들어감"의 원인이었다. 목표 재선택, 출구, 명령 덮어쓰기를 차례로 의심하며 네 판을 헛돌았다(local84~87). 새 부대 종류를 만들면 **먼저 "원작의 어느 판단표가 이 부대를 도는가"를 확인**한다.
- **사용자가 "~처럼 움직인다"고 말하면 그 기능의 코드를 먼저 볼 것.** "공성 부대처럼, 적 접근 시 공격이 켜진 것처럼"이 정확한 진단이었다.
- **증상이 같은데 고쳐도 그대로면 가설을 바꾸기 전에 로그를 더 넣을 것.** 출현 칸은 `retake_first_step`(원작이 저장한 첫 칸)과 `sortie_young_born`(실제 출현 칸)을 같이 찍고 나서야 "저장은 맞는데 출현이 다르다"는 것이 보였다.
- **기존 일꾼 코드를 빌려 쓰면 그 코드의 다른 규칙도 따라온다.** 거점 일꾼 단계가 매 턴 목표를 다시 골라 부대를 적 밀집 지역으로 돌렸다(local84). 빌려 쓸 때는 그 흐름이 명령을 쓰는 곳을 전부 훑는다.
- **새 옵션의 기본값을 "끄면 이전 판"으로 두는 관행이 사용자의 고정 규칙을 옵션으로 만들 수 있다.** "위임 군단은 컴퓨터 규칙에서 반드시 제외"가 기본 꺼짐 옵션이 되어 있었다(local94에서 고정). 사용자가 "반드시"라고 한 규칙은 옵션으로 만들지 않는다.
- **사용자 말이 모호하면 한 줄로 되물을 것.** "공성을 off"를 기능 전체 끄기로 읽어 한 판을 되돌렸다(local90→91). 실제 뜻은 수복 부대의 건설이었다.

## G. v16~v16.1 배포 세션에서 한 실수 (2026-11-15, local170~local176)

### G1. 원인 확인 전에 고침 (등용 다중 선택 재선택)

### G11. 숨김과 그리기를 따로 결정하고, 안전장치는 기본으로 꺼 둠 (조조전 그림, 2026-11-16)
- 조조전 그림은 게임 스레드가 원작 모형을 숨기고 렌더 스레드가 따로 그렸다. 숨김은 그리기 성공을 보지 않았고, "못 그리면 원작 모형" 안전장치(local61)는 설치기 기본 0인 `sprite_fallback`에만 있었다. 그리기가 어떤 이유로든 멈추면 공개판 사용자에게는 부대가 통째로 사라지고 돌아오지 않았다. 이 문제를 고친 여러 판(local7~local61)이 개발 PC 설정(`sprite_fallback=1`)에서만 확인됐다.
- **규칙:** 원작 것을 숨기는 기능은 숨기는 쪽이 대체물이 실제로 나간 증거(대상별, 짧은 유효 시간)를 보고 결정한다. 안전장치는 항상 켜고, 스위치는 더 엄격하게 만드는 쪽에만 둔다. 실패한 자원·항목은 다시 시도한다. 고친 동작은 설치기 기본값으로 확인한다.

### G12. 그리기 지점을 한 해상도 기록에 맞춰 바꾸고, 실게임 없이 설치를 이어 감 (조조전 그림, 2026-11-16, local195~199)
- local195에서 "1920×1080 화면이면 UI 깊이가 장면 깊이로 잡힐 수 있다"는 가설로 늦은 깊이 규칙을 넣었는데, 기록된 결합 순서(1280×720)에 대고 결정 규칙을 한 번도 돌려 보지 않았다. 그 결과 그리기가 후처리 중간으로 당겨져 그림이 덮였고, 제출만 본 증명이 모형을 숨겨 부대가 통째로 사라졌다. 이어서 기준 지점(1920×1080 패스)이 이벤트 프레임에만 있다는 것도 원경 기록을 보기 전까지 몰랐다. 그사이 조조전을 끈 실행만 있어서 local195~197이 실게임 확인 없이 쌓였다.
- **규칙:** 그리기 지점·패스 판정을 바꾸면 남아 있는 결합 순서 기록(근경·원경·이벤트) 전부에 새 규칙을 대 보고, 모든 기록에서 같은 위치를 고르는지 확인한 뒤 빌드한다. 숨김 증명은 "제출"이 아니라 그림이 살아남는 지점이어야 의미가 있다. 렌더 경로를 바꾼 판은 그 기능을 켠 실게임 확인 전에 다음 렌더 변경을 쌓지 않는다.

### G13. 설치 전 검사가 정합성 경로를 빼먹고, 같은 컴파일을 매번 반복함 (2026-11-16 점검)
- 설정 키 두 개(local195 `ccz_sprite_fault`, local196 `ccz_draw_probe`)를 `installer_map.json`에 넣고 모듈 명세(`development/modules/ccz-sprites/module.json`, `module_catalog.json`)를 다시 만들지 않았다. `dll-split`에는 `always` 경로가 없어서 local195~199 설치를 다섯 번 통과했고, 전체 경로 기준 실행에서야 `module-manifests` 실패로 드러났다.
- 같은 날 측정: 설치 한 번에 큰 번역 단위(SAN14_Convenience, 최적화 CPU 약 54초)를 진단판·배포판·검사마다 다시 컴파일했다. 입력이 같은 경로도 `-Feature` 모드에서는 캐시를 쓰지 않았다.
- **규칙:** 설치는 `tools/local_install.ps1`로 하고, 이 스크립트는 `always` 경로를 먼저 돌린다. 설정 키를 더하면 `gen_installer_catalog.py --apply`와 `gen_module_manifests.py --apply`를 함께 돌린다. PowerShell 5.1의 `ConvertFrom-Json`은 JSON 배열을 객체 하나로 내보내니 `| ForEach-Object {$_}`로 풀고 개수를 확인한다(빌드 캐시 첫판이 이 때문에 큰 DLL 하나를 "캐시됨"으로 건너뛰었다).
- 캐시를 붙인 첫판은 콜드 `dll-split`이 106초에서 139초로 오히려 느려졌다. 경로가 통과할 때마다 스케줄러 스레드에서 하위 프로세스로 입력 키를 다시 계산해 기다리던 단계가 묶였다. **규칙:** 스케줄러 콜백에서는 무거운 일을 하지 않는다(기록은 실행 뒤 한 번에). 속도 개선은 캐시 적중뿐 아니라 콜드 실행도 바꾸기 전과 함께 재서 보고한다.

### G14. 코드를 옮기면 텍스트를 읽는 검사가 조용히 덜 본다 (번역 단위 분리, 2026-11-16)
- `native_adapter.cpp` 머리를 `native_core.inl`로 옮기고 지형 함수에서 `static`을 떼자, 어댑터 텍스트를 읽던 검사 13경로가 실패했다. 더 나쁜 건 실패하지 않은 쪽이었다. `switch_deps.py`는 기능 깃발 128개를 전부 놓치고, 술어도 17개에서 15개로 줄었다(바깥으로 나간 `terrain_foam::active`·`terrain_render::active`를 정규식이 못 찾음). 그런데도 통과했다. 소스 스냅숏 내보내기의 기준 문자열, 조언자 점검, 훅 지도 소유자 이름도 옛 위치를 보고 있었다.
- 단일 단위에서는 `static`이던 지형 `restore()`가 외부 함수가 되자, 링커가 그 함수를 버리지 못해 단일 단위 모의 검사 7개가 BCrypt 링크 오류를 냈다. 쓰는 파일(`native_water_diag.inl`)에 `#pragma comment(lib,"bcrypt.lib")`를 두는 것이 기존 관례(`save_host.h`)와 맞았다. 스크립트마다 라이브러리를 더하는 방식은 되돌렸다.
- 코드 배치가 바뀌면 DLL 문자열 목록에서 앞에 붙은 이웃 바이트(실수 상수·숫자표)가 바뀐다. 문자열 하나하나 비교는 이것을 "잃은 문자열"로 보고하므로 원본 리터럴 기준 규칙을 만들었다(REFACTOR_EQUIVALENCE 1절). 첫 판은 `.inc` 파일을 읽지 않아 계절 엔진 로그 문구를 검사하지 못했고, 단순 정규식 대조로 찾았다.
- 내 스크립트가 줄 끝이 섞인 파일(`verify_diplomacy_intel.py`, 지형 모듈 2번째 줄)의 CRLF를 통일해 버렸다. 바이트 그대로 다시 고쳤다.
- **규칙:** 정의를 다른 파일로 옮기면, 옮기기 전에 `tests/`·`tools/`에서 원래 파일 이름과 옮길 `static <이름>` 텍스트를 찾아 읽는 검사를 모두 고친다(공용 읽기는 `tests/hub_text.py`). "통과"만 보지 말고 검사가 찾은 개수(깃발·술어·계약 수)를 HEAD와 비교한다. 분리 단위가 다른 단위의 동적 초기화 변수를 읽지 않는지 `unit_equivalence.py audit`로 확인한다. 소스를 고치는 스크립트는 파일마다 BOM과 줄 끝을 보존한다. 문자열 비교 도구를 고치면 판독기를 독립된 방법으로 대조하고 실제 빌드 빨간 검사로 확인한다.

### G15. 과수집이 누락을 가렸다 (검사 캐시 키, 2026-11-16)

### G16. 두 단위가 함께 읽는 헤더의 상태는 글자 검사로 다 못 잡는다 (ui 번역 단위, 2026-11-16)

### G17. 진단 스위치가 DXGI Present 슬롯을 직접 고쳐 시작 시 튕김 (local205, 2026-11-16, 같은 사고 두 번째)
- 첫 번째는 2026-10-31 조조전 그림 local1이다(`CCZ_SPRITES.md` 15줄): `unified_overlay::present`와 Steam `gameoverlayrenderer64`가 서로 불러 0xC00000FD. 게임 스왑체인 생성 전에 Present 훅을 걸어 Steam이 그 위에 다시 훅을 건 것이었다. 그 규칙은 기능 문서에만 적혀 이 교훈집에 오지 않았고, 그래서 gpu_profile 설계와 이번 원인 찾기 모두 그것을 못 봤다.
- `gpu_profile`은 11-02에 만든 직접 패치(DXGI 팩토리 CreateSwapChain, 스왑체인 vtable Present)를 그대로 썼다. 그 사이 11-05에 Present 훅 소유가 Layout으로 넘어갔는데, 진단 경로는 기본 꺼짐이라 함께 돌려 본 적이 없었다.
- 덤프(0xC00000FD): `gpu_profile::present`와 Steam 오버레이가 4936번 번갈아 불렀다. Layout 탐침이 64x64 스왑체인을 만든 직후부터다. 첫 사고와 합치면(덤프 자체에는 코드 메모리가 없음): Steam 오버레이는 스왑체인이 새로 생길 때마다 그때 Present 슬롯에 든 함수를 걸고 자기 원본으로 삼는다. 그래서 우리 훅이 Steam의 원본이 되었고, 우리 훅은 Steam이 건 DXGI Present를 불러 고리가 생겼다. 이 추정이 맞으면 Layout 자신의 Present 훅도 Layout이 설치된 뒤 게임이 스왑체인을 새로 만들 때 같은 위험이 있다(주 세션에 넘길 것). 같은 슬롯 때문에 Layout은 자기 Present 훅을 거부했다(`layout_refused … 3`). 그래서 "관찰만" 하는 스위치가 모든 Layout 오버레이를 껐다.
- **규칙:** 공유 COM 슬롯(DXGI Present·팩토리)은 소유자(Layout) 말고는 아무도 쓰지 않는다. 다른 모듈은 Layout 구독을 쓰고, Present 앞 지점밖에 없으면 게임 쪽 값(장치 필드, 게임이 직접 재는 시각)으로 나머지를 채운다. Present 슬롯에 함수가 들어간 뒤 새 스왑체인이 생기면 Steam 오버레이와 고리가 생기므로(두 번 겪음), 탐침을 일으키는 구독은 게임 스왑체인이 생긴 뒤에 한다. 기본 꺼짐 진단 경로도 공유 훅 소유가 바뀌면 함께 켜서 한 번 돌려 본다. 덤프가 있으면 스택의 반환 주소 빈도부터 센다(스크립트로 몇 분, 추측보다 빠르다). 튕김을 진단할 때는 먼저 `rg -i "gameoverlayrenderer|C00000FD" docs`로 같은 서명이 기록됐는지 찾는다. 한 기능에서 얻은 공통 위험(공유 훅, 외부 오버레이)은 기능 문서와 함께 이 교훈집에도 적는다.

### G18. 원작 "최종" 건설 판정이 해방(정책 잠금) 검사를 건너뛴다 (local214, 2026-11-17)

### G30. 진단판 전용 기능을 시험 기능으로 공개할 때 세 곳이 함께 움직인다 (다중 일기토, local289 / v16.6, 2026-11-21)

- 공개 무로그 빌드에서 그 기능 경로는 처음 컴파일·실행되므로, 노트에 "진단판으로 확인, 공개 DLL로 켠 상태는 미확인"을 나눠 적는다.
